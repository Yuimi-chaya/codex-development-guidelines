# Model Research and User-Selected Roles

Use during deliberate adoption when model recommendations are relevant, a requested detailed model/configuration consultation, or an intentional refresh. Do not run a market survey in every coding thread. A consultation may remain read-only and does not require a policy source unless the user also wants a policy draft. Recommendation, selection, policy writing, benchmarking, and installation are separate decisions.

## Start with the exposed inventory

Read the actual provider/harness inventory through permitted tools. Record exact selectable IDs, provider, reasoning controls, per-agent overrides, visual input, tool access, and session-sharing constraints. Do not scan credentials or private configuration to discover hidden models. Public availability does not prove availability in this account or execution role.

If enumeration is unavailable, use explicitly supplied facts with provenance and label unverified controls. Do not invent a model, select a similar-looking name, or claim that an override occurred. Disclose any permitted harness-default fallback.

## Verify public information

Search the public web for the exposed model identities using official model/release documentation and the relevant provider's pricing and capability documentation. Fetch the supporting pages, not only snippets. Resolve provider aliases only with evidence; a label resembling a public model is not proof of that backend. Do not send keys, private endpoints, nonpublic deployment IDs, or sensitive configuration to search engines. For a private alias, use a verified public mapping or leave identity unknown.

Record source and check date for material claims. Distinguish announcement, availability, snapshot, and alias dates. Do not infer a release date from a version number or claim the newest exposed name is the newest public model. When sources disagree, report the disagreement; when browsing is unavailable or declined, provide a clearly limited comparison without fabricated current prices or rankings.

Separate current-provider charges from upstream list prices. Include currency, units, input/cached-input/output, applicable image/tool/reasoning charges, and batch or other conditions where documented. An upstream price is background evidence, not the user's verified bill. Do not infer an effective price from a subscription label or assume a markup.

Speed evidence should distinguish time to first token, output throughput, tool/network waits, and end-to-end task time. Label provider claims, published benchmarks, local observations, and unknowns separately. Note reasoning settings, output length, concurrency, and task/tool conditions where available; results under different conditions are not a controlled comparison.

## Recommend by role, not a universal ladder

| Role | Capability gate | Preferences after the gate |
|---|---|---|
| Throughput and discovery | Adequate extraction, locating, summarization, and instruction reliability | Prefer recent releases, low applicable cost, and fast useful throughput; an older better fit remains eligible |
| Ordinary implementation and verification | Sufficient coding, tool use, and test interpretation for the scope | Balance completion quality, cost, and time |
| Advanced interactive execution | Relevant visual interpretation, parameter/action understanding, and actual tool/session access | Compare complete-task success, latency, retries, media load, and handoff cost |
| High-risk architecture and review | Strong reasoning and evidence evaluation for the risk | Prioritize quality and appropriate independent checks within the user's budget |

These are suggested responsibilities, not mandatory agents or one fixed ranking. One model may cover several roles. An executor may use the same or a stronger model than the primary Agent. A strong coding score alone does not establish strong UI execution; do not require weak-model failure before a difficult interactive task receives an appropriate model.

For browser/Computer Use, separate interaction method, model, execution context, and resource limits. Prefer authorized structured access for equivalent work, and isolate long/high-output interaction when the executor has the required capabilities. Keep a bounded observe-decide-act stage with its owner; do not recommend permanent per-click tutoring by the primary. Short direct work and unavailable isolation remain subject to the user's browser policy.

## Present a shortlist

Use a compact comparison for candidates relevant to the user's roles, not an exhaustive provider dump. Include:

| Field | Required distinction |
|---|---|
| Identity and access | Exact exposed ID/provider, verified public identity or unresolved alias, usable roles/tools |
| Release | Relevant release/snapshot dates and which kind of date each is |
| Cost | Applicable provider rates/units/conditions; upstream-only or unknown explicitly labeled |
| Capability | Evidence relevant to the proposed role, limitations, reasoning/tool support |
| Speed | First-token, throughput, whole-task evidence and its conditions; unknown where unmeasured |
| Recommendation | Role fit, reason, alternative, tradeoffs, and confidence |
| Provenance | Sources, check date, observed versus published versus inferred |

Explain whether the user is trading money, waiting time, reliability, or retained context, rather than collapsing them into an unexplained score. Hypothetical round-count arithmetic is allowed only when labeled illustrative, not as a measured benchmark.

Do not run paid probes or benchmarks merely to fill missing cells. Such tests require applicable authorization, bounded cost/time, appropriate fixtures, and no unapproved external side effects. If approved, measure complete tasks and failures as well as successful individual calls. Do not install a benchmark dependency without permission.

## Let the user decide

Ask for unresolved role/model/reasoning choices and fallback authority using the relevant questions in [interview.md](interview.md). Reuse explicit choices; a rejected recommendation is not a reason to keep persuading or silently substitute a model. Offer a permitted disclosed default or deferred choice when exact selection is unsupported.

For interactive work, resolve only relevant priorities, direct-use exceptions, and progress/stop limits. A model upgrade does not grant more permissions or reset the stage's retry/resource budget. Retention and media controls remain separate; do not promise that closing an executor deletes its history.

If adoption proceeds, put approved operational mappings and limits into self-contained effective instructions. Keep research tables, volatile prices, and question text out of runtime policy; an optional [adoption record](profile.md) may preserve requested provenance. Ordinary tasks reuse approved mappings. Refresh only affected choices when availability, meaning, or the user's priorities change.
