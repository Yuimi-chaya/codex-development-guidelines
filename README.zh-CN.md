# Codex AGENTS.md 基础开发准则

[English](README.md)

面向 Codex 用户级 `AGENTS.md` 的基础开发准则。根据真实环境、已有配置和用户偏好生成可直接使用的指令；明确指定时也可以配置项目级规则。行为原则可用于其他 Agent，但安装流程以 Codex 的配置机制为准。

核心设计原则是：

> 先检查能够查明的事实，再给出有依据的建议，集中询问尚未确定的偏好，最终由用户选择。规则应适配用户，而不是要求用户适配维护者的模型、工具和工作方式。

用户要求安装这些准则后，[`adopt-agent-policy`](skills/adopt-agent-policy/SKILL.md) 会先检查环境、相关 Codex 配置和实际暴露的模型，核对公开资料，再把建议与待决定事项一起交给用户。无需先挑规则、选访谈模式或逐条回答编号题目；已有偏好直接复用，已有 `AGENTS.md` 按语义合并。

默认目标是实际 Codex 配置目录中的 `AGENTS.md`：使用 `CODEX_HOME`，未设置时为 `~/.codex`。写入前检查 `AGENTS.override.md` 是否遮蔽普通文件，并展示准确路径、差异和恢复方案。仅安装 Skill 包、审阅仓库或开发本仓库，不等于授权修改本机配置。

## 为什么需要这个仓库

Agent 规则并不是一套可直接复制的万能模版， 而是要从真实环境与用户偏好出发， 尽可能的将规则覆盖至常见场景来尽可能的减少问题的发生， 并使运行过程更加符合你自己的偏好：

- 永久行为和临时环境事实；
- 安全边界和个人偏好；
- 普通开发和少见的媒体/浏览器任务；
- 运行时执行和首次安装；
- 主代理职责和子代理路由；
- 项目规则和用户级配置。

本仓库把这些层次分开：

| 层次                         | 职责                            | 典型生命周期    |
| -------------------------- | ----------------------------- | --------- |
| 运行时 `AGENTS.md`            | 工作期间的范围、所有权、安全、委派、工具、恢复和真实性规则 | 每个相关任务    |
| `adopt-agent-policy` Skill | 配置时先探测和检索，再推荐、集中询问、合并与验证 | 安装/更新会话期间 |
| 已采用的用户/项目指令                | 实际生效的语言、Shell、委派、资源和授权范围      | 改变或不再适用之前 |
| 可选采用记录                     | 为后续审阅保存选择来源，不是运行时加载器          | 更新或移除之前   |
| 运行时事实                      | 当前 Shell、路径、工具清单、模型能力、权限和硬件   | 当前会话或任务   |
| 任务决策                       | 本次是否需要媒体处理、检查点、浏览器角色、笔记或重型命令  | 当前任务      |

## 按板块拆分

简洁的运行时基线描述“做什么”，独立模块解释“何时、为什么、怎么做”：

| 板块                                                      | 解决的问题                |
| ------------------------------------------------------- | -------------------- |
| [上下文与记忆](references/modules/context-and-memory.md)      | 如何复用真实上下文，而不是重新访谈用户？ |
| [委派与工具](references/modules/delegation-and-tools.md)     | 主代理负责什么，何时委派、验证和接管？  |
| [媒体与传输](references/modules/media.md)                    | 如何在保留证据的同时控制上游负载？    |
| [环境与阻力](references/modules/environment.md)              | 何时自行适配，何时暂停并询问更好的工具？ |
| [文件与恢复](references/modules/files-and-recovery.md)       | 哪些内容必须保留，什么才算真正可恢复？  |
| [验证与资源](references/modules/validation-and-resources.md) | 能声称完成到哪一步，哪些进程应继续运行？ |

这些是编写和审阅准则用的模块，不是每个编码线程必须额外预读的六份文件。生成的目标指令应当自包含；条件规则在触发时执行，不能因为某个数值偏好没配置，就让保护失效。

权限边界、运行默认策略、可配置参数要分开。例如，媒体原件应保留、传输前应检查，但审查尺寸按任务选择；子代理默认最多定向重试一次，用户可以明确调整次数，但不能因此失去停止条件。规范条数由需要区分的行为决定，不设固定数量。

## 运行时规范应该约束什么

运行时基线描述 Agent 已经开始工作后应如何行动。

### 适配真实用户和环境

Agent 应自动检测事实，而不是猜测。它应根据真实的 Shell、路径、仓库、权限、工具、模型清单、网络条件和用户偏好工作。

这不代表要用户确认每个事实，而是要区分：

- 检测事实：“当前运行的是 PowerShell 7”；
- 用户偏好：“以后优先使用 PowerShell”；
- 任务决策：“本次命令应使用 PowerShell，因为当前会话就是 PowerShell”。

### 根据用户要求与任务需要来选择模型等级

主代理负责推理、整合、最终决策、验证和面向用户的结论。其他获准角色可以负责互不重叠的文件写入，但最终责任仍在主代理。子代理只有在能带来吞吐、隔离、工具访问或独立审查收益时才值得使用。

浏览器/Computer Use 同时考验界面理解与多轮工具交互。执行模型必须理解视觉状态、通过工具参数表达正确动作，并识别动作后的状态。便宜快速的模型不能仅因“会点击”就被视为够用；也不能仅因工具是图形化的，就一律使用昂贵模型。

四个选择应分别判断：

| 决策    | 怎么选择                                    |
| ----- | --------------------------------------- |
| 交互方式  | 等价工作优先采用合适且获准的结构化访问，但不能绕过必需的 UI 测试或工具限制 |
| 模型    | 先满足相关视觉/工具能力，再比较实际成本、延迟和可靠性             |
| 执行上下文 | 考虑输出量、时长、工具/会话访问、协调成本和交接信息损失            |
| 资源策略  | 按需限定有效进展、步骤/时间/费用、媒体传输和实际支持的留存行为        |

长流程或高输出交互默认优先交给合适的独立执行代理，**不代表必须用弱模型**。执行代理可以使用与主代理同级甚至更强的模型，但要核实其真实视觉输入、工具、权限和会话访问；模型名可选，不等于执行能力相同。

| 情况               | 用户已批准策略内的建议路径                          |
| ---------------- | -------------------------------------- |
| 稳定、重复、低风险操作      | 已证明够用的快速执行模型，或工具支持且获准的自动化              |
| 陌生界面、困难视觉判断或复杂状态 | 直接使用有能力的交互执行模型，无须先让弱模型失败               |
| 长流程且工具返回很多       | 使用能力足够的独立执行代理，可以采用昂贵模型                 |
| 极短操作、交接成本明显更高    | 适用授权允许时，由主代理有限直接执行                     |
| 必需会话或工具无法委派      | 采用允许的替代方式、已有有界 fallback，或询问限定范围的直接操作例外 |

比较完整任务结果，而不是单次点击费用。总耗时包含模型响应、工具/页面等待、网络传输、交互轮数、交接、纠错和验收。假设快模型每轮 3 秒、用了 30 轮，轮次耗时为 90 秒；强模型每轮 8 秒、用了 8 轮，则是 64 秒。如果两者轮数相同，快模型就可能更适合。所以不能假设强模型一定更慢，也不能假设它一定少走弯路。

委派应以有界阶段为单位，例如筛选、导出并验证报告；观察、判断、行动的闭环留在执行代理内，不让主代理逐张截图检查、逐次点击辅导廉价模型。切换操作者前停止原操作者，交接已核实状态、待确认副作用、权限边界和剩余预算。同一可变会话只有一个活跃操作者。

短操作和隔离不可行时的直接执行，仍须符合既有授权或限定例外。没有子代理、主模型能力更强，都不能覆盖明确的浏览器禁止项。交付简洁结论和关键证据，而非完整会话；主代理核验不要求重放所有点击。[委派模块](references/modules/delegation-and-tools.md)详述路由、进展信号与接管。

### 注意媒体可能带来的上游网络负载与本地储存压力

媒体上传前要检查尺寸、单文件大小和批量总量，原件保留在本地。对于 4K 视频检索，可以采用：

1. 在本地定位相关时间点；
2. 抽取代表性画面；
3. 裁剪到真正需要检查的区域；
4. 不需要像素级保真时生成压缩审查副本；
5. 只上传能够回答问题的最小集合；
6. 原视频和全分辨率画面继续保留在本地。

例如，一批 4K 视频抽帧可能包含单张超过十 MB 的文件，多张原样上传会带来网络压力和上游 `payload too large` 风险。这是工作负载示例，不是某个 API 的统一上限。应检查实际字节数与请求封装开销；工具上限未知时先做小批次代表性传输，不要编造上限。

压缩不能破坏证据：细小文字、透明通道和像素级检查可使用无损局部裁剪。有些工具会自动返回截图，不能控制时应避免再次复制；不要主动把 base64 塞进线程。交给子代理也不会消除上游传输和存储成本。

三个预算要分开：模型输入/上下文、网络请求字节数、持久化会话历史。隔离主要控制回流到主线程的证据，不一定控制工具 payload 或宿主存储；关闭执行代理也不能证明截图已删除。仅使用真实支持的输出/留存控制，并披露无法控制之处。本仓库提供指导，不是传输层或存储层的实现。

保留原件与审查副本的对应关系、时间戳；涉及 UI 坐标时，还要保留裁剪偏移和缩放关系。审查缩略图不自动等于工具的操作坐标空间。执行代理返回的路径须对审阅者可访问；否则通过允许的渠道传递必要的优化证据。

### 独立审阅子代理结论

子代理提供的是证据和建议，不是不可质疑的事实。每次委派都应有：

- 明确目标；
- 明确输入；
- 预期输出或证据形式；
- 所有权边界；
- 停止条件。

结果不合格时默认最多定向重试一次，明显无提升空间时更早接管。重试失败、方向偏离或超过进度边界后，结束委派并重新判断。反复认错控件、缺少观察信息、页面故障、权限不足不是同一种问题；更换模型、方法或环境必须确实针对阻碍，且处于授权范围内。

接管是承担下一步判断责任，不是自动使用被禁止的工具。更换代理不能重置失败阶段的重试/资源预算；重复动作前先核实尚未确定的副作用。不无限等待或反复辅导同一个代理。延迟本身不证明能力不足：先设定适合任务的进度边界，使用有界等待，可行时继续推进独立工作。

主代理要亲自核对关键证据，例如检查相关文件、复现声称已修复的问题，或核实结论的来源。这不要求重新播放每次浏览器点击，也不要求读完所有原始输出。但如果任务较简单可以较轻松完成就不要再应付规则来创建子代理。

大量文件探索在可用且获准时交给只读子代理，返回路径、符号、行号和压缩结论。注意分工与双方的推进节奏：先明确各自负责什么、哪些步骤依赖对方的结果，主代理推进独立工作，双方及时交流会影响任务的阻碍和变化，避免重复探索和频繁询问无变化的状态。

长时间编译或测试可以由获准的子代理陪跑，观察已有进程并报告有效进度、失败或退出结果。陪跑不等于再启动一份编译，也不增加重型任务的并发额度。若子代理无法访问执行会话，使用支持的观察方式或由主代理监控，不声称已完成不存在的委派。

### 向用户提问或提醒

长任务需要持续推进，也需要及时对齐需求。缺少的信息会实质影响方案或结果、且无法从现有上下文合理确定时，Agent 应提出具体、简短的问题，有必要时提供有意义的选项。已明确的答案直接复用，普通任务不重启配置问卷。

需要用户打开窗口、复现问题或提供即时协助时，应按用户偏好使用可用且获准的交互工具，例如 `request_user_input`，明确请求什么、为什么需要。不能默认用户把应用放在前台，也不能只在进度消息里提一句，就假设用户已经看到或完成。

例如，排查某个应用需要用户打开其设置窗口。Agent 可以发起协助请求，同时继续检查不依赖这个窗口的源文件；需要截图的步骤则等用户确认或实际观察到窗口后再做。没有回复不等于已完成操作，也不能自动转去执行未经授权的 GUI 操作。

提问工具只用于明确的问题或协助请求，不用于普通进度、致歉或承诺。用户指出误用后，直接纠正，不再弹出“是否同意我不再误触”之类的确认框。避免空调用和对同一个未变化的请求反复提醒。

等待期间推进独立工作，依赖回复的步骤保持待定。工具的模式、输入格式和审批限制始终适用；工具不可用或用户不愿启用时，通过允许的渠道明确询问，不假称提醒已送达，不把沉默或超时当成授权。交互工具是否触发系统通知、用户是否看到通知，需要实际验证。

### 环境形成阻力时停止硬重试

当 Shell、终端、依赖、网络、权限或工具形成明显阻力时，Agent 应：

1. 识别观察到的阻碍；
2. 判断是临时问题、语义问题还是环境问题；
3. 找出可行替代方案；
4. 说明每个方案的成本、范围和风险；
5. 在安装工具、修改全局配置、切换环境或扩大权限前询问。

已有、等价、获准的工具可以直接采用，不必重启设置访谈。提议新安装时，除成本外还应说明来源/版本、范围和恢复方式，不确定的信息如实标注。

用户明确要求坚持某种方法时，应尊重并解释局限，但不能把它当作安装工具、修改全局配置、绕过访问控制或无限重试的授权。询问应针对新的决定，而不是把整套采用问卷重问一次。

### 按风险匹配恢复和验证

对于多文件逻辑、已验收行为、迁移、媒体、广泛配置、删除或返工等恢复成本明显的修改，应先建立任务级检查点，且不能混入用户无关工作。

Agent 要区分已实现、已测试、真人验收、已发布、已安装、受阻和未知。静态检查通过不等于真人验收或部署成功。

二进制 Git diff 不一定是完整备份：暂存状态、未跟踪图片、被忽略素材可能需要单独保护，必须检查恢复点实际覆盖什么。获准保留的开发服务器也不是“构建没结束”，应报告 URL 和生命周期，同时确认有限命令已退出。不要终止用户自己的进程。

### 面向读者编写正文

README 用于介绍项目及其使用方式，PR 正文用于说明变更及验证情况，发布说明用于告知版本变化。正文应提供这些实际内容，而不是记录助手如何接到要求、准备写什么或修改了几轮。

写作时要区分三件事：作者掌握哪些背景，文档写入了哪些信息，读者到当前段落已经能理解什么。不能因为某个定义在全文中出现过，就默认读者看到一个含糊指代时会自动联系到它。

先交代理解或执行下一步所必需的概念、对象和条件；引用较远的内容时，简短重述要点，或指出准确的章节及其用途。读者可能通过目录、链接或滚动直接进入某个章节、示例或操作步骤，应在这些位置附近提供必要背景。可合理依赖目标读者的专业常识，不必在每段重复全部定义。

#### 示例：发布说明的语气

假设某报表工具新增了 CSV 导出功能，需要向使用者发布版本说明。

不合适：“按你的要求，我已经加好了导出功能。”

合适：“新增 CSV 导出功能。”

两句话描述同一项功能；后一句直接说明版本变化，不需要读者知道谁向助手提出过要求。

#### 示例：让操作提示可独立阅读

假设某文件工具的“保留原件”选项会将修改另存为副本。需要在保存窗口中提示用户如何保留原文件；窗口不展示使用手册里的选项列表。

不合适：“选择前面介绍的第一种方式保存。”

合适：“保存时选择‘保留原件’，将修改另存为副本。”

操作说明直接给出选项名称和结果，读者不必回翻寻找“第一种方式”指什么。

#### 示例：提供正文而非写作清单

假设一个 PR 修复了空报表导出时的崩溃，相关的三项回归测试通过，完整测试套件尚未运行。需要编写 PR 摘要。

不合适：“在这里说明修复内容、测试结果和剩余风险。”

合适：“修复空报表导出时的崩溃。三项相关回归测试通过；完整测试套件尚未运行。”

摘要只使用情境给出的事实，不把“该写哪些内容”当成正文，也不扩大测试结论。

审阅时，先按正文顺序检查前提与指代，再单独读可能独立进入的章节和示例。若必须借助编写对话、猜测对象，或在脑中补上一段解释才能理解，就应补足正文。示例中的实际文本还应与情境逐项对应。

口吻按用途选择：邮件可以采用用户指定的第一人称，PR 应保留真实的变更、测试和风险说明，必要的署名或披露也应保留。有关写法的指令属于写作指南；标为成品的示例则必须给出实际成品。

## 偏好不是问卷

以下选择经过批准后，可以写进实际生效的 `AGENTS.md`。不应该混进去的是收集这些选择的问卷：

- 首选 Shell 和次级 Shell；
- 持久的 CPU 或 worker 限制；
- 同时运行的重型任务数量；
- watcher 是否可以继续运行；
- 具体模型和 reasoning 映射；
- 子代理深度和角色路由；
- 主代理 UI 操作的限定例外、交互进展限制和升级权限；
- 媒体传输预算；
- 实际支持的证据留存偏好及已知控制限制；
- 笔记保存和可见性；
- 远程发布权限；
- 依赖安装策略；
- 回复语言和详细程度。
- 是否启用主动询问和协助请求、可用交互渠道及减少打扰的偏好。

`adopt-agent-policy` 把适用且获批的偏好合并到实际用户/项目指令里。可选的[采用记录](skills/adopt-agent-policy/references/profile.md)仅在需要时保存选择来源，不默认创建；本仓库没有自动 profile 加载器。没有这份记录、甚至没有本仓库时，普通任务也应能够工作。

用户已经明确给过的偏好应复用。可选未知值可以保留为带已披露 fallback 的条件规则；缺少回答不等于允许安装、上传、发布或扩大权限。

## 模型与环境推荐

### 是否启用主动询问

首次配置或用户有意调整沟通方式时，先检测实际交互工具与模式限制，再把是否愿意启用主动询问、保持现状或暂缓决定纳入集中配置建议，解释及时对齐和打扰成本。普通线程复用这一选择；不启用可选功能也不代表 Agent 可以猜测关键答案。

对于支持该功能的 Codex 版本，可以提出以下配置建议：

```toml
[features]
default_mode_request_user_input = true
```

已有 `[features]` 时只添加或修改这一项，不重复创建表格。是否支持、当前是否已启用、目标配置范围以及是否需要重启应在实际配置时核对。展示最小差异、备份和恢复方式，用户批准后才写入；不自动改 `config.toml` 或重启应用，也不保证仅写入规则就能使当前任务获得工具。

功能示例和使用动机来自[维护者的使用记录](https://x.com/heyiwei233/status/2109408871941034316)。2026 年 10 月 12 日核对的[官方配置 schema](https://developers.openai.com/codex/config-schema.json)包含这一布尔配置项，但不证明所有版本都支持或一定会通知用户。详见[包内交互配置流程](skills/adopt-agent-policy/references/user-interaction.md)。

### 在配置阶段检索实际暴露的模型

用户要求安装时，代理主动完成实际模型清单检查和相关公开资料核对，再给出选型建议；已有有效映射优先保留。用户要求的详细配置咨询或有意刷新也可进行检索。普通线程复用已批准的选择，不在开场重新给市场上的模型排名。只读咨询可以止于推荐，不必生成规范或安装任何东西。

从用户运行环境实际暴露的准确模型 ID 和供应商开始，检查真实的 reasoning、视觉、工具和单代理控制。上网检索并阅读官方发布/模型文档及相关供应商价格；供应商别名必须有身份依据，不能按名字猜后端，也不能把私有部署标识送去搜索。无法核实的信息标为未知。

按相关候选提供简表：

| 字段    | 比较中应说明什么                            |
| ----- | ----------------------------------- |
| 身份与发布 | 准确暴露 ID/供应商、已核实公开映射、发布/快照日期及日期类型    |
| 能力    | 对拟定角色有意义的证据、视觉/工具访问、reasoning 控制和局限 |
| 成本    | 当前供应商费率、币种/单位/条件；区分仅上游标价与未知费用       |
| 速度    | 首字延迟、输出速率、完整任务观察及测量条件               |
| 推荐    | 角色适配、取舍、备选、置信程度、来源和核对日期             |

建议按吞吐/检索、普通实现/验证、高级交互执行、高风险架构/审阅分工。吞吐层先满足能力和可靠性，再优先考虑发布较近、速度快、成本低的候选；“近期”不是排除更适合的旧模型的硬规则。高级交互执行可以有意使用昂贵模型；长流程在工具与权限允许时优先使用独立执行上下文，短操作仍遵守已有的直接操作权限。

最终模型和 fallback 由用户选择。不得静默替换成推荐项、擅自付费跑基准、安装测试依赖或保存未批准映射。无法联网或缺少可比较测量时如实披露。易过期的研究表格不进入运行时指令，只有批准的操作选择才进入。详见[包内模型选型流程](skills/adopt-agent-policy/references/model-selection.md)。

### 检验工具，但仍然以用户的偏好为准

采用阶段检查相关终端宿主、当前 Shell/版本、编码行为、工具可用性和 Git 状态。这些是检测事实，不是修改机器的授权。

Windows 上可在核对版本行为后，为更一致的 UTF-8 默认行为推荐 PowerShell 7，同时说明外部程序与旧编码仍需单独处理。可以为状态/diff 检查及可恢复的任务级历史推荐 Git；两者都不是采用行为准则的强制前提。

解释收益、兼容成本、拟安装项的来源/版本、范围、风险、恢复方式和“保持现状”的替代方案。用户保留当前 Shell 或非 Git 工作方式时，适配命令并使用已核实的原样备份；不能自动安装 Git、初始化仓库、设置全局身份/配置、修改默认 Shell 或发布。[环境模块](references/modules/environment.md)提供具体示例。

## 安装时先查什么，再问什么

安装只有一条主流程，检查深度由实际需求决定。代理先完成可访问的只读检查，不要求用户先选模式或模块：

| 先主动查明 | 形成什么建议 |
| --- | --- |
| 实际 Codex 配置目录、现有指令、覆盖文件及相关设置 | 准确写入目标、保留哪些本地规则、是否存在遮蔽或冲突 |
| 当前 Shell/版本、相关编码行为、Git 和工具可用性 | 适配现状的做法，以及可选工具的收益、代价和保持现状的方案 |
| 实际暴露的模型与可用控制 | 核对发布、能力、供应商价格和速度证据后，给出角色与模型建议 |
| 提问工具、模式限制、可观察的功能状态 | 是否启用必要主动询问，以及不启用时的允许渠道 |
| 文件编码、换行、权限、hash、恢复点及适用的指令链加载预算 | 最小差异、备份，以及合并后是否会被截断 |

读取相关配置只提取必要字段，不倾倒整个 `config.toml`，不读取认证文件，也不把密钥、私有地址或部署名发送到搜索引擎。模型清单、速度或价格查不到时标明未知，完成其他检查后继续提出有限建议，不无限探测，也不编造数据。

文件成功写入不代表规则全部加载。合并前应按当前版本的发现规则，核对适用指令链的字节数与有效上限，包括相关的 `project_doc_max_bytes` 设置。已知超限时，提出保留必要行为的去重/精简方案，或请求明确的配置调整；不能静默截断、删除用户内容或提高上限。无法核实时，说明加载完整性尚未验证。

随后集中展示已查事实、已复用偏好、推荐配置及理由，只询问真正需要用户决定的部分，例如模型策略、主动询问、资源偏好、现有规则冲突。提问工具有数量限制时按支持的格式组织；只有答案产生新的依赖或冲突才继续追问。无需讨论的数字限制可以采用已披露的保守策略，不必每个条目都问一次。

例如，假设检查发现 Windows 上仍用 PowerShell 5.1，未安装 Git；用户已指定中文、保留默认模型、禁止自动安装，且没有指令覆盖冲突。代理应保留这些选择，在同一份建议里解释 PowerShell 7 和 Git 的可选收益，说明本次继续适配现有环境，再集中解决尚未明确的主动询问偏好和实际文件变更。它不应重新问语言、让用户从规则库挑条目，或把安装工具当成前提。

建议可以包含完整 diff 和准确操作范围。仍需授权时，对这个具体结果请求确认；已经明确授权的同一操作不再重复询问。`AGENTS.md`、可选 `config.toml` 修改、额外工具安装和应用重启各有独立范围，但可以在同一轮列清并由用户一并选择。提问工具不能替代其规则禁止的审批机制。

## 最终写入什么

安装结果是一份能直接使用的 `AGENTS.md`：只有适用行为与获批偏好，使用描述性标题和普通列表。不包含规则库的 `[CORE-001]`、`[SUB-007]` 等维护 ID、题目编号、模块状态表、模型研究表、版本来源记录或安装过程旁白。

例如，关于简单任务和委派的规则可以写成：

```markdown
简单任务由主代理直接完成。大量文件探索在可用且获准时使用只读子代理；
明确分工、证据和停止条件，主代理核验关键结论后负责最终验收。
```

规则库中的编号用于维护、翻译和升级比对，保留在仓库内。Skill 自带的双语底稿由规则源生成，只移除编号，不缩减行为边界；验证器检查底稿与规则源同步。升级时，旧安装文件里误带的仓库维护编号应列入清理差异，保留对应行为。用户原有文件中的项目引用或自定义编号应按实际用途保留，不能全局删标签。

## 怎么使用

可以直接让 Agent 使用本地仓库配置，无需先安装 Skill：

```text
使用这份仓库的 skills/adopt-agent-policy，为我配置 Codex 用户级 AGENTS.md。
先主动检查相关配置、环境和实际暴露的模型，核对公开资料。
复用已有偏好，把推荐、尚待决定的问题和拟写入的差异集中给我。
```

只需要安装可复用 Skill 时，明确要求从选定版本安装 `skills/adopt-agent-policy`；这一步不会同时改写 `AGENTS.md`。安装包自带流程和规则底稿，无需另找仓库源。确实指定另一份 checkout/release 时使用指定源，不猜测安装目录旁边存在仓库。`skills/maintain-development-notes` 按需单独安装，已有目标先比较。

后续有意升级时使用 `workflows/UPDATE.md`，只重新讨论变化的决定。旧记录缺失不应阻止语义比对。其他 Agent 可以借鉴行为准则，但必须适配其实际指令发现、模型控制和安装机制，不能照搬 Codex 路径。

## 采用流程

用户要求采用本仓库时：

1. 阅读适用的用户/项目指令和恢复笔记；
2. 自动检测环境与当前运行时能力，不要求用户确认客观事实；
3. 核对相关公开模型资料，形成带证据、替代方案和未知项的建议；
4. 复用已有答案，集中询问真正未决的偏好和冲突；
5. 语义合并目标指令，保留本地修改，生成不带维护编号的自包含正文；
6. 展示具体 diff、准确范围、编码、备份、恢复点和能力 fallback，解决尚缺的授权；
7. 只应用获批修改，核验 hash、最终差异、覆盖关系和正文；报告实际写入与待加载状态。

详见 [`workflows/ADOPT.md`](workflows/ADOPT.md)。

## 边界案例

| 情况                      | 运行时行为                       | 采用行为                            |
| ----------------------- | --------------------------- | ------------------------------- |
| 普通新编码线程                 | 使用已有运行时规范和当前事实              | 不启动访谈                           |
| 首次安装准则                  | 先完成相关配置、环境和模型检查            | 推荐完整配置，集中询问未决项，默认用户级目标 |
| 主代理拥有浏览器权限              | 有合适角色时优先路由给执行角色             | 只有用户要建立可复用委派 profile 时才配置角色映射   |
| 4K 视频画面单张 14 MB         | 检查并生成较小审查传输，原件留在本地          | 只有媒体属于 profile 时才询问持久预算         |
| 子代理返回不确定诊断              | 审阅证据，有限重试，必要时接管             | 只有建立可复用委派 profile 时才配置重试偏好      |
| 依赖安装连续失败                | 停止，解释替代方案，修改环境前询问           | 只有需要持久化时才记录网络/工具偏好              |
| 用户要求 push               | 检查已配置权限，必要时询问               | 可以在采用时配置发布权限，但当前 push 仍要遵守适用授权  |
| 新线程没有采用记录               | 读取实际生效的指令                   | 不为重建记录而重启完整访谈                   |
| 子代理不可用且禁止直接浏览           | 使用允许的结构化替代方法，或询问本次例外        | 不静默扩大权限                         |
| 用户只要求审阅规范               | 只读提供审阅结果                    | 不强制进入安装访谈                       |
| 昂贵模型最适合困难 UI 工作         | 在可行且获准的执行代理中使用，不要求先让廉价模型失败  | 由用户选择角色映射和 fallback             |
| 执行代理返回大量截图后关闭           | 保留关键证据，不声称历史已删除             | 只记录实际支持的留存控制                    |
| 供应商暴露的别名没有公开身份依据        | 仅使用已批准的已知能力/fallback，披露不确定性 | 不虚构发布时间、价格或已核实后端                |
| 用户拒绝 PowerShell 7 或 Git | 适配保留的环境和合适备份                | 不强制安装或反复劝说                      |
| README 草稿依赖上一轮聊天或未交代的指代 | 补足必要背景与实际内容，按阅读顺序核对事实和指代    | 不为一般写作检查启动配置访谈                  |

主动交互的边界案例：用户已同意必要提问时直接复用，不每次重问；用户暂缓启用时保留必要澄清的允许渠道；需要人手打开窗口时等实际确认后再继续依赖步骤；编译陪跑只观察已有任务，不重复启动。配置偏好、实际写入和重启的授权范围须明确，可以集中处理。

## 语言和本地化

英文和简体中文规则源使用相同稳定 ID，并应保持行为等价；安装正文移除这些维护 ID。目标通常只安装一种运行时语言。可以维护独立伴随翻译供人工审阅，但把两份完整规范同时放入运行时文件会增加上下文消耗并产生翻译漂移风险。

## 验证

在仓库根目录使用 PowerShell 7：

```powershell
pwsh -NoProfile -File ".\scripts\validate-repository.ps1"
pwsh -NoProfile -File ".\scripts\test-validator.ps1"
```

验证沿用仓库已有的 PowerShell 工具链，不要求采用者为了使用准则切换 Shell。验证器检查文本编码、本地链接、规则库关系、决策检查表覆盖、Skill 元数据、无维护编号底稿及其与源文件的同步关系。回归测试在临时副本中注入损坏场景，不会安装任何东西。它们都不能证明翻译语义完全等价或 Agent 一定按流程行动。

维护者修改双语规则源后，运行 `pwsh -NoProfile -File ".\scripts\sync-policy-assets.ps1" -Write` 更新安装底稿，再运行上述检查。此脚本只更新仓库内底稿，不会安装或修改用户的 `AGENTS.md`。

[审阅场景](tests/policy-scenarios.md)用于单独的行为场景走查，或未来隔离环境中的前向测试。应记录实际运行了哪一种，不能把主代理走查说成独立执行测试。

针对正文可读性，[阅读案例](tests/artifact-reading-cases.md)提供完整的待审片段和单列的审阅要点。先只读片段，再对照要点，检查缺失前提、模糊指代、错误概括和占位内容。结构校验通过不代表读者理解这些片段时没有困难。

## 状态和发布

本仓库提供配置级准则，是否安装、如何取舍由用户决定。不能因为仓库出现新文件，就自动 push、创建 PR、合并、发布、安装，或修改用户现有的 `AGENTS.md`。安装包或指定源应来自可识别的版本，并保持本地修改可恢复。
